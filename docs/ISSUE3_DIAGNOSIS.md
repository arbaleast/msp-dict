## 1. 方法与格式基准

格式基准来自 imewlconverter 现行源码（2026-05 重构后）：

- `src/ImeWlConverter.Formats/Win10Ms/MsChxUdpExporterBase.cs`
- `src/ImeWlConverter.Formats/Win10Ms/MsChxUdpImporterBase.cs`
- 仓库内真实样本 `微软五笔UserDefinedPhrase.dat`（144 字节，2 条记录）

关键字段语义（与本项目此前理解不同）：

| 偏移 | 含义 | 合法值 |
|---|---|---|
| 0x18 | 文件总大小 | 等于实际字节数 |
| 0x20 | Unix 时间戳 | 当前时间 |
| 0x24–0x3F | 保留 | 必须全 0 |
| 记录 +0x06 | **同一拼音下的候选序号** | 1 起，UI 只展示 1–9 |
| 记录 +0x08 | 固定 0 | 0 |
| 记录 +0x0C | **2000-01-01 纪元秒** | 当前 Unix 秒 − 946684800 |
| 记录 +0x10 | 拼音 UTF-16LE | 仅 `a-z` 与 `'`，≤32 单元 |
| 记录词区 | 词条 UTF-16LE | ≤64 单元 |

真实样本校验通过（2 条，候选位均为 1，记录时间戳为 2000 纪元秒），
说明本项目新校验器与 Windows 侧真实文件一致。

## 3. 根因逐项

### 3.1 候选序号写成词频（P0，核心）

`src/builder_win10.py`（修复前）：

```python
entry += bytes([rank & 0xFF, self.ENTRY_FLAG])   # rank 来自 cli 传入的原始词频
```

`src/cli.py` 把 `msp_*.txt` 第三列词频原样传入。词频可达数千万，
`& 0xFF` 后落在 0–255 的任意值：

- `0`：微软拼音候选位从 1 起，0 是非法值；
- `10–255`：超出 UI 的 9 个候选位，Windows 导入校验失败或行为未定义。

这正是 Issue 中「导入失败，文件格式错误或文件已损坏」的直接原因，
也是候选列表/管理页异常的来源。

### 3.2 无拼音词条 → 0 长度编码记录（P0）

`rime-ice` 的 `tencent.dict.yaml` 是「词 + 词频」两列（无拼音），
合并脚本把它写成 `词条\t\t100`。旧构建器不校验空拼音：

```
hanzi_offset = 18 + 0 = 18   → 编码长度 0
```

imewlconverter 的导入器对 `codeBytesLen <= 0` 直接判定记录无效；
1.99M 条里 47% 是这种记录，Windows 解析必然失败。

### 3.3 设置页转圈（P0，Windows 侧缺陷）

> **2026-11-21 更正**：本节原先把卡死归因为「词库规模超过 Windows 2 万条导入上限」，
> 该结论错误。微软从未公布自定义短语的数量上限；「2 万条」是
> **自学习词库**（`ChsPinyinUDL`）的容量，与自定义短语不是一个库。
> 详见 [#3 更正说明](https://github.com/arbaleast/msp-dict/issues/3#issuecomment-7061114819)。

真实机制：

- 进入「设置 → 词库和自学习 → 用户定义的短语」时，页面把
  `%APPDATA%\Microsoft\InputMethod\Chs\ChsPinyinEUDPv1.lex` 里的**全部短语**
  一次性物化成 UI 列表（无虚拟化、无分页、无上限），耗时与内存随条数线性增长；
- 实测量级：600 万条约占 9 GB、十几分钟仍加载不出（MS Q&A 3743529），
  约合 1.5 KB/条；
- 「清除」按钮位于该页面内，必须先进入页面才能点，而一进页面就开始全量加载，
  于是**用户无法自救**（逻辑死锁）——这也是「点了清除也卡死」的原因；
- 输入引擎本身不受影响：导入后打字能正常出候选，只有设置页打不开。

因此：

- 这**不是** `.dat` 的格式问题，`python -m src.cli validate` 通过即代表文件合法；
- 恢复方式为删除 `ChsPinyinEUDPv1.lex`（先备份），见 [RECOVERY.md](RECOVERY.md)；
- 档位不再按「设置页是否会卡」设计，改为按词汇覆盖面划分，见 `src/profiles.py`。

### 3.4 时间戳（P1，非阻断）

- 文件头 0x20 写 `0`（旧构建器默认 `timestamp=0`）；
- 记录 +0x0C 写死 `0xE679CD20`（来自 imewlconverter 2017 版注释中的旧值，
  按 2000 纪元解释是 2122 年）。

新实现改为 Unix 秒 + 2000 纪元秒，与现行 imewlconverter 一致。

### 3.5 README 与 CI 不一致

修复前 `.github/workflows/biweekly-build.yml` 只产出：

```
msp_full.dat  msp_freq10.dat  msp_freq50.dat  msp_freq100.dat  msp_freq500.dat
```

而 `README.md` 推荐下载 `msp_win10.dat`（~27 万），没有任何步骤生成它。
`scripts/update_readme.py` 还把 `msp_freq100` 的词条数写进 `msp_win10.dat` 行，
进一步放大了不一致。

## 4. 附件中的 Windows 文件鉴定

| 文件 | 大小 | 头部 | 判断 |
|---|---:|---|---|
| `ChsPinyinUDL.dat` | 32,768 B | `55 AA 88 81 02 00 60 00 55 AA 55 AA` | Win10 微软拼音**自学习词汇**库；0x0C 计数 = 390，0x14 时间戳；0x2400 起为数据区（实际布局与 imewlconverter 的 60 字节导出不完全一致） |
| `ChsPinyinIH.dat` | 392,900 B | `55 AA 88 80`，0x0C 计数 = **6,463** | Windows 内部用户词条存储（与 UDL 同族、变体不同），非 mschxudp |
| `ChsPinyinDeletedCands.dat` | 1,024 B | `DEL ` | 删除候选记录 |

结论：

1. 三者**都不是** `mschxudp` 导入文件，无法用本项目格式直接校验；
   它们是 Windows 导入后写入的内部库。
2. `ChsPinyinIH.dat` 只有 6,463 条，而旧推荐档 28.7 万条——若该文件是导入后的
   用户短语库，说明 Windows 实际只保留/接受了不到 2.4% 的词条。
3. UDL 的 60 字节记录布局与 imewlconverter 的「自学习」导出也并不完全一致，
   进一步说明这些是 Windows 私有存储，不能作为格式基准。

## 6. 编辑器批量导入性能（O(N²) → O(N)）

旧 `MSPinyinEditor.add_entry` 每条都要线性扫描「待添加列表」，批量导入是 O(N²)。
改为 `text -> DictEntry` 哈希索引（`_index` + `_pending_add`）后单条 O(1)，
并在 `parse_bytes` 后重建索引，保证索引与底层列表一致。

实测（同一台机器、`BatchImporter.import_txt`，仅导入不保存）：

| 规模 | 旧实现（00aa6a0） | 新实现（导入） | 新实现（导入 + 保存） |
|---:|---:|---:|---:|
| 1,000 | 0.011 s | — | — |
| 2,000 | 0.035 s | — | — |
| 4,000 | 0.126 s | — | — |
| 8,000 | 0.497 s | — | — |
| 10,000 | 外推 ≈ 0.8 s | 0.026 s | 0.084 s |
| 100,000 | 外推 ≈ 78 s | 0.255 s | 0.870 s |
| 200,000 | 外推 ≈ 310 s | **0.552 s** | 1.858 s |
| 300,000 | 外推 ≈ 700 s | **0.855 s** | 2.842 s |

外推按 O(N²) 从 8,000 条的 0.497 s 计算；新实现 20 万条导入 0.55 s、含保存 1.86 s。
